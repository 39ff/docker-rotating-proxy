# Design: gost v3 replacement (Plan A)

This document explains how the gost-v3 based stack works, why it is built
this way, what it gives up compared with the Squid stack, and what was
verified. Versions: `gogost/gost:3.3.1` (go-gost/x v0.27.1),
`qmcgaw/gluetun:v3.41.3`, Python 3.9+ standard library for the generator.

## Architecture

```
                        docker host  (published on ${BIND_ADDR:-0.0.0.0})
 clients                +--------------------------------------------------------------+
 (allowlisted IPs,      |  gost container "dockergost_rotate"  (one process)           |
  optional user/pass)   |                                                              |
   |                    |  service rotate :3128 --> chain pool --> hop "upstreams"     |
   +---- :3128 -------->|     admission allowlist      selector round, maxFails 2,     |
   |                    |     [auther users]           failTimeout 60s, reload 30s    |
   |                    |                              nodes = config/nodes.json       |
   |                    |                                    + fail-closed backup node |
   |                    |                                                              |
   +---- :30000 ------->|  service static-30000 --> chain static-30000 --> 1 node -----+--> socks5/http/https
   +---- :3000N ------->|  service static-3000N --> chain static-3000N --> 1 node --+  |    upstream proxies
                        |                                                          |  |
                        |  metrics 127.0.0.1:9000 (healthcheck only)               |  |
                        +----------------------------------------------------------|--+
                                    compose network (not published)                |
                        +-----------------------------+                            |
                        | gluetun "dockervpn_1"       |<---- http dockervpn_1:8888 -+
                        |  HTTP proxy :8888, kill     |------ OpenVPN ------------------> VPN provider
                        |  switch, DNS over the tunnel|
                        +-----------------------------+   (one container per openvpn/<name>/)

 files (generated by setup/generate.py, config/ is bind-mounted read-only as a directory)
   config/gost.yaml        services, chains, hops      -> container recreate on change
   config/nodes.json       rotating pool               -> re-read every 30 s
   config/allowed_ip.txt   admission whitelist         -> re-read every 30 s
   config/users.txt        auther                      -> re-read every 30 s
   openvpn/<name>/gluetun.env, gluetun.conf            -> env_file / mount of the VPN container
```

## Components and why

### gost v3 (one container for everything client-facing)

The old stack had three moving parts on the request path: Squid (rotation and
allowlist), one gost v2 container per SOCKS/HTTP upstream (protocol
conversion and static port), and gluetun. gost v3 does rotation, protocol
conversion, static ports, allowlist, auth and metrics in one process:

- **Rotating pool** is a top-level hop `upstreams` whose nodes come from
  `config/nodes.json` (`file` data source, `reload: 30s`) with
  `selector: {strategy: round, maxFails: 2, failTimeout: 60s}`. The `rotate`
  service has `handler.retries: 2`, so a failed dial is retried on the next
  nodes before the client sees an error (the role of Squid's
  `connect-fail-limit` + trying the next `cache_peer`).
- **Static ports** are one service + chain with a single inline node each.
- **Allowlist** is an `admissions` entry with `whitelist: true` (gost's
  default mode is *blacklist*; the generator always sets it and a unit test
  enforces it), attached to every service.
- **Optional auth** is an `authers` entry with a file data source, attached to
  every handler when `template/users.txt` has a user.
- **Healthcheck** uses gost's metrics endpoint on `127.0.0.1:9000` from inside
  the container (busybox `wget` is in the image). Nothing is sent to the
  internet.
- **No resolver** is configured: gost passes the target hostname to the
  upstream (SOCKS5 domain address type / HTTP `CONNECT host:port`), so there
  is no local DNS lookup of targets, and node addresses such as
  `dockervpn_1:8888` resolve through Docker's embedded DNS.
- Per-request rotation over keep-alive connections: the HTTP handler reads
  requests one by one and its upstream transport has keep-alive disabled by
  default, so every request dials a new route. `CONNECT` tunnels pick one node
  per tunnel. Both are verified end-to-end.
- `dialTimeout: 10s` per service bounds slow/dead upstreams (Squid had
  `connect-timeout=8`).

### The fail-closed node (important)

gost v3 **fails open**: when a hop has no node to select, the chain produces
an empty route and gost dials the target **directly**
(`x/chain/route.go: chainRoute.Dial` falls back to `DefaultRoute`). That
happens when `nodes.json` is empty, missing, or unparsable at a reload
(`x/hop/hop.go: reload` replaces the node list even when loading failed). A
direct connection would expose the server's own IP, which Squid prevented
with `never_direct allow all`.

Mitigation: the hop always contains one inline node `fail-closed`
(`127.0.0.1:9`, nothing listens there, `metadata.backup: true`). The backup
filter keeps it out of the rotation while any real node is available; when
the file yields no nodes it is the only candidate, the dial is refused and the
client gets `503`. When all real nodes are marked failed, gost's "last resort"
picks the first failed node, which is again `fail-closed` because inline
nodes come first. Verified both ways (see below). Static chains always have
exactly one node and cannot become empty. A chain that references an unknown
hop name would also become a direct route, so the generator only references
the hop it defines (unit-tested).

### gluetun (unchanged role, hardened wiring)

gluetun stays: it turns an `.ovpn` into an HTTP proxy with a firewall kill
switch and DNS over the tunnel, and it is maintained. Changes: pinned tag and
digest; the `.ovpn` is bind-mounted read-only as `/gluetun/custom.conf`
instead of mounting the whole directory read-write; credentials come from
`env_file` (`gluetun.env`, generated from `secret`, single-quoted so `$`, `#`,
spaces and `"` survive compose's dotenv parser); `HTTPPROXY_STEALTH=on`; no
published ports (gost reaches `dockervpn_N:8888` over the compose network,
gluetun's firewall accepts its local subnet); the dead shadowsocks mapping is
gone.

**Correction to the original assumption**: rewriting `remote <hostname>` to an
IP is *not* optional. gluetun v3.41.3's custom provider refuses hostnames
(`internal/openvpn/extract/extract.go`: "host is not an IP address"; verified
by running the container, see below). It also removes every `remote` line and
writes back a single `remote <ip> <port>` built from the first one, so
multiple remotes and `remote-random` never worked with gluetun. The generator
therefore leaves the user's file untouched and, only when a hostname is
present, writes a resolved copy `openvpn/<name>/gluetun.conf` (git-ignored)
that is mounted instead. An unresolvable hostname is a hard error (nothing is
written), so VPN static ports never shift silently.

### setup/generate.py (Python standard library)

Replaces PHP 7.4 + composer + symfony/yaml. It validates input (warnings with
file:line, invalid lines skipped), never writes a partial configuration, and
writes every file atomically (temp file + `rename`), which matters because
gost re-reads the data files every 30 s. Output is deterministic (same input,
same bytes) and a second run reports "unchanged". YAML is emitted by a small
block-style emitter; strings that are not plain identifiers are JSON-quoted,
which is valid YAML (so `on`, `30000:30000`, `${BIND_ADDR...}` cannot be
misread). A unit test round-trips the output through PyYAML when it is
installed.

`docker-compose.yml` carries a label with the SHA-256 of `config/gost.yaml`
(and of the mounted `.ovpn` for each VPN). gost has no safe in-place reload of
its main config (SIGHUP reload is unreliable, go-gost/gost#754), and compose
does not look into bind-mounted files, so the label is what makes
`docker compose up -d` recreate exactly the containers whose config changed.

## Old problems and how they are addressed

| problem in the Squid version | now |
|---|---|
| `b4tman/squid:5.8` (2023) with unpatched CVEs | no Squid |
| `ginuerzh/gost:latest` (v2, unpinned), `qmcgaw/gluetun` unpinned | `gogost/gost:3.3.1@sha256:...`, `qmcgaw/gluetun:v3.41.3@sha256:...` (multi-arch index digests) |
| PHP 7.4 (EOL) + composer to dump YAML | Python 3.9+ stdlib, runs on the host or in `python:3.13-alpine` |
| compose `version:` key | removed |
| gost/gluetun ports on 0.0.0.0 without auth or ACL | all client ports behind the allowlist (+ optional auth); gluetun not published; `${BIND_ADDR}` |
| credentials in `docker-compose.yml` | VPN: `env_file`; proxies: `config/*.json/yaml` (0600, git-ignored) |
| generator rewrites the user's `.ovpn` | user file untouched; resolved copy only when needed |
| dead `50000:8388` mapping | removed |
| cron: `docker run -it`, overwrites `proxyList.txt`, SIGHUP to Squid | `set -euo pipefail`, no TTY, separate `publicProxyList.txt`, keeps the old list on a bad download, `--nodes-only`, no restart |
| healthcheck through the rotation to httpbin.org every 5 min | local metrics endpoint |
| no `.gitignore` | generated files and secrets ignored (CI checks `git status` is clean after generating) |
| `:` split breaks IPv6 | `[addr]:port`, bare IPv6 rejected with a hint |
| no validation, tests, CI | validation with line numbers, 50 unit tests, CI with compose validation and e2e |

## Trade-offs vs. the Squid stack

Gained: one container instead of 1 + N on the request path, hot reload of
the pool, allowlist and users without restart (the cron no longer touches a
container), allowlist and auth on every port, fail-closed VPN path and pool,
smaller attack surface (no Squid, no PHP), arm64 images for both components.

Given up or changed:

- **No caching and no Squid ACL language.** The old config had
  `cache deny NOCACHE` with `NOCACHE = src all`, so caching was off anyway.
  Squid's `Safe_ports`/`SSL_ports` (only ports 80/443, `CONNECT` only to 443)
  have no equivalent here: gost forwards to any target port. That is more
  permissive for allowlisted clients.
- **Header scrubbing.** Squid removed client-sent `X-Forwarded-For`, `Via`
  and `Cache-Control`. gost adds none of these and strips
  `Proxy-Authorization`, but passes headers the client itself sends. gost adds
  `Proxy-Agent: gost/3.0` to responses towards the client (not the target).
- **Plain HTTP via HTTP upstreams uses `CONNECT`.** gost's HTTP connector
  always opens a `CONNECT host:port` tunnel (`x/connector/http/connector.go`),
  also for `http://` URLs. Squid's `cache_peer` forwarded those as normal
  absolute-URI `GET` requests. Upstreams that only allow `CONNECT` to 443 (the
  Squid default) will reject plain-HTTP targets; HTTPS targets are
  unaffected. This hits public proxies and `httpsquid` entries most. gluetun's
  proxy and SOCKS5 upstreams are not affected.
- **Error responses.** Denied clients are disconnected without an HTTP answer
  (Squid sent a 403 page). Failed upstreams give `503`.
- **Failure memory is short.** Every reload (30 s) rebuilds the node objects,
  which resets their failure counters, so a dead upstream gets two new
  attempts every 30 s (measured, see below). `retries: 2` hides this from the
  client unless several consecutive picks are dead, which is likely with a
  large, mostly dead public list.
- **Fail-closed costs some availability.** Once every real node is marked
  failed (2 failures within 60 s each), requests get `503` until the next
  reload (at most 30 s) or `failTimeout` instead of gost retrying a failed
  node as its "last resort". Not leaking the server IP was judged more
  important.
- **Restarts for structural changes.** Adding a static port, a VPN or turning
  auth on recreates the gost container (a second or two without any port).
  Pool/allowlist/user changes need no restart.

## What was verified, and how

All on 2026-10-23, Docker 29.9.2 + compose v5.6.1, with the pinned images.

1. **Full end-to-end run** (`ci/e2e.sh`, the same script CI runs): three
   upstreams (`gogost/gost:3.3.1` as socks5 `user1:pass1`, socks5
   `user2:pa:ss2`, http `user3:pass3`) plus one auth-less HTTP proxy for the
   public list, each with a fixed IP on a test network, and a host-side
   origin that answers with the client IP, i.e. the upstream that reached it.
   Results:
   - `:3128`, one request per connection:
     `172.30.99.12 .13 .11 .12 .13 .11` (strict round robin over 3 nodes)
   - two requests on one keep-alive connection: `.12 .13` (per-request
     rotation)
   - `CONNECT` tunnels (`curl -p`): `.11 .12 .13`
   - `:30000/:30001/:30002` always `.11/.12/.13` (plain and `CONNECT`, x6)
   - allowlist: a client container at `172.30.99.20` was served before and
     disconnected on `:3128` and `:30000` after `config/allowed_ip.txt` was
     rewritten without it, while the host client was still served (no restart)
   - `nodes.json` reduced to one node: within the reload interval all answers
     came from `.12`; gost's `StartedAt` unchanged
   - `nodes.json = []`: `HTTP 503`, and the origin never saw gost's own IP
     (gost could reach the origin directly, so a fail-open would have shown)
   - `publicProxyList.txt` + `--nodes-only`: the public proxy joined the
     rotation, static ports unchanged, gost not restarted
   - `template/users.txt` populated + `docker compose up -d`: compose recreated
     gost (hash label), then on `:3128`, `:30000`, `:30002` no credentials
     `407`, wrong password `407`, correct `200`; `CONNECT` with credentials
     `200`
   - the generator skipped an invalid line and a CRLF duplicate with warnings
   The run takes about 2 minutes. Locally `nofile=65536` could not be granted
   (sandbox hard limit 20000), so a local-only override lowered it
   (`E2E_EXTRA_COMPOSE`). On GitHub Actions (run 39995021057, all four jobs
   green) the generated file ran unchanged and produced the same answers.
2. **Fail-open without the sentinel** (host gost binary 3.3.1 copied from the
   image): same config with `nodes.json = []`; without the `fail-closed` node
   the request returned `HTTP 200` via a direct connection, with it `HTTP 503`
   (`dial tcp 127.0.0.1:9: connect: connection refused`). With two dead
   upstreams in the pool, 10 requests all returned `503`; the debug log shows
   each dead node tried twice, then only `fail-closed@127.0.0.1:9`, and the
   origin received no request at all.
3. **Failure counter reset on reload**: pool `[dead, live]`, `maxFails 2`,
   `failTimeout 60s`, `reload 5s`, one request per second: the dead node was
   dialed again after every reload (timestamps 14s, 19-20s, 25-26s, 29-30s,
   35-36s) instead of being skipped for 60 s; all client requests still got
   `200` thanks to `retries`.
4. **gluetun**: with the sample `openvpn/` dirs the generated stack started;
   gluetun accepted `/gluetun/custom.conf` and the `env_file` credentials
   (masked in its settings summary), listened on `:8888` and tried the
   resolved/IP remotes. While the tunnel was down, gost's `:30003`/`:30004`
   answered `503` (gost reached `dockervpn_N:8888`; gluetun refused to
   forward), i.e. no leak. Mounting the original Surfshark `.ovpn` with a
   hostname made gluetun exit with `host is not an IP address`. No real VPN
   connection could be established (placeholder credentials, sandbox egress).
5. **compose**: `docker compose config -q` on the generated sample;
   `BIND_ADDR=127.0.0.1` and `[::1]` resolve to `host_ip`; compose recreates a
   container when an `env_file` value changes; single-quoted env values keep
   `$`, `#`, `"` and spaces literally.
6. **Generator**: 50 unit tests on Python 3.9 and 3.13 (via the official
   Alpine images, as in CI); the PyYAML round-trip test passes where PyYAML
   exists; `docker run python:3.13-alpine python3 setup/generate.py` works as
   documented; second run is a no-op.
7. **Cron script**: with a local list server: good list -> `publicProxyList.txt`
   replaced and `nodes.json` regenerated, `proxyList.txt` untouched; HTML
   instead of a list -> exit 1, previous list kept; HTTP 404 -> exit 22,
   previous list kept. `shellcheck` clean.
8. **Source reading** (go-gost/x v0.27.1, gluetun v3.41.3) for: admission
   whitelist semantics and empty-list = deny all, auther empty = deny all and
   `user` without password = any password (the generator never writes such
   lines), hop reload behaviour, the HTTP connector always using `CONNECT`,
   no `X-Forwarded-For`/`Via` added, gluetun's firewall accepting its local
   subnet.

Not verified: a real VPN tunnel end to end, arm64 hosts, IPv6 clients,
`https` upstreams (TLS dialer) and the public list against the internet.

## Known limitations and follow-ups

- `CONNECT` for plain HTTP via HTTP upstreams (see trade-offs). If this
  matters, a follow-up could route `http://` traffic of `httpsquid`/public
  entries through a small forwarding hop or keep a Squid parent just for them.
- Failure counters reset every reload. Options: a longer `reload` (slower
  pickup), gost's per-node `probe` (active health checks, also rebuilt on
  reload), or regenerating `nodes.json` only with recently working proxies
  (a checker in the cron job).
- No target-port restriction (`Safe_ports`); could be added with a gost
  `bypass` on the services if wanted.
- `https` upstreams are not certificate-verified (gost default, same as v2);
  a `secure: true` option per line would need a format extension.
- Hostname -> IP resolution of VPN remotes happens at generation time; rerun
  the generator when the provider's IPs change.
- VPN numbering follows alphabetical directory order; adding a directory that
  sorts earlier shifts later VPN ports (proxy ports are unaffected).
- Files with credentials are 0600; with Docker `userns-remap` the container
  may not be able to read them (rootless Docker and Docker Desktop are fine).
- The compose services use the `json-file` log driver with rotation
  (10 MB x 3) because gost logs one line per request (client IP, target host).
- `BIND_ADDR` applies to all ports; separate binds for rotate/static would be
  an easy extension.
- **Country-based pools** (out of scope): add one hop per pool, each with its
  own file (`nodes-jp.json`, `nodes-us.json`) and the same fail-closed node,
  one chain per hop and one service/port per chain (for example 3129 = JP,
  3130 = US); the generator would take the pool name from an extra column or
  from separate list files. Selecting the pool by username on a single port
  would need gost's routing/matcher features and is not explored here.
